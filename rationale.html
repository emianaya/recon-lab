Why this theme, and this approach

I picked Theme 1 because tomographic reconstruction sits at an unusually good intersection for a demo like this: it's a real, well-posed physical and mathematical system, not a toy; most engineers have heard "CT scan" and "PET scan" without knowing how either actually produces an image; and—less obviously—the failure mode of iterative reconstruction is exactly the bias–variance tradeoff every ML engineer already has intuition for from training curves. That last point is what decided it over a more generic concept explainer: I wanted the tool's "aha" to transfer directly to something the reviewer already understands, not teach an isolated fact.

The approach follows from that: rather than illustrate the idea with a diagram, the tool actually runs it. A sparse Radon-transform system matrix, a Poisson noise model, and two real reconstruction algorithms (MLEM and filtered backprojection) execute client-side, live, with no backend—so the object you draw, the dose you pick, and the curve you watch are the real computation, not a canned sequence standing in for one.

What makes it interesting, or non-obvious

Most "explain X" tools show a finished picture or play a fixed animation. Here, the reconstruction panel is a live 100-iteration optimization you can grab and scrub anywhere along—drag the chart, and both the iteration slider and the reconstructed image follow, in either direction. Draw your own object on the 64×64 canvas and it goes through the identical scan-and-reconstruct pipeline as the built-in phantoms; there's no special-cased "demo" path.

The less obvious choice was putting the error-vs-iteration chart, not the reconstructed image, at the center of the design. The picture is the hook. The chart—where the data-fit curve keeps improving while true error bottoms out around iteration 10 and then climbs—is the actual point: early stopping as regularization, made physical instead of abstract. A "BEST" marker you can click jumps straight to the optimal stopping point, so the gap between "the algorithm says it's still improving" and "the image is actually getting worse" is something you click through, not something you're told.

Key design decisions and tradeoffs

One shared Radon model for PET and CT, not two

PET (ring of detectors, coincidence events) and CT (rotating source, fan of rays) look different in the scanner animation, but both feed the same parallel-beam sinogram and the same reconstruction code underneath.

Tradeoff: not physically precise for CT's actual fan-beam geometry. I judged the shared model was the right call for a demo whose point is the reconstruction algorithm's behavior, not scanner geometry—and said so directly in the UI rather than letting a reviewer assume more rigor than is there.

Tests target the math, not the pixels

The reconstruction math (recon-math.js) is a standalone module loaded by both the browser page and a Node test suite—so tests exercise the real implementation, not a hand-copied stand-in that could drift. The suite is property-based: an adjoint test (⟨Ax,y⟩ ≈ ⟨x,Aᵀy⟩, which came back to machine precision—relative error 7×10⁻¹⁰), a point-source sinusoid check, mass conservation, MLEM's log-likelihood monotonicity and count-preservation identities, FBP linearity.

Tradeoff: writing property tests took longer than eyeballing the reconstructed image and moving on. It's also what actually caught real bugs during development—including a genuine clamping bug in the chart's y-axis that a purely visual check had missed.

Numbers before pixels

The iteration count, dose default, and chart axis scale weren't tuned by eye. I ran the MLEM loop headlessly across dose levels first, measured where the true-error minimum actually falls, and picked settings (100 iterations, low-dose default) so the "money shot" reliably lands somewhere visible on a plain linear axis—rather than reaching for a log axis to paper over a minimum that was avoidably squeezed against the edge.

Tradeoff: more upfront measurement work than shipping a plausible-looking default and adjusting later from vibes.

Auto-run everywhere, no inert start screen

The scan runs on load, and changing the phantom or the dose slider triggers an immediate rescan—no "Start" button gatekeeping the first thing a reviewer sees.

Tradeoff: less deliberate pacing for a first-time user, but it matters directly for the take-home's "self-contained evaluation" requirement: someone should see the tool doing something the moment the link opens, not an empty shell waiting for input.

FBP's cutoff and MLEM's iteration count, as the same idea twice

FBP's "smooth ↔ sharp" slider and MLEM's iteration count are framed as two knobs on the identical resolution/noise tradeoff, sitting side by side at equal visual weight—rather than treating FBP as a footnote to the "real" iterative method.

Tradeoff: more surface area to build and test than shipping MLEM alone, but it's what makes the regularization idea generalize instead of reading as one algorithm's quirk.

Working with Claude Code

I used Claude Code throughout, in an iterative build-critique-verify loop rather than a single prompt-and-accept pass. A few concrete moments that shaped the result:

  • When the true-error minimum looked squeezed against the chart's edge, my first instinct was a log axis. Claude built that, but I pushed back once I looked at it properly—the real issue was iteration count and a y-axis clamping bug, not the axis scale. We ran the actual numbers headlessly before I accepted the fix, rather than trusting how it looked.
  • I asked for real tests, not a claim that things worked—specifically an adjoint test, since a mismatched forward/backprojector is the classic silent bug in reconstruction code. Claude proposed the specific test list; I had it show me the test code and the run output before I'd treat any correctness claim as settled.
  • Before calling the deploy done, I had Claude run the Playwright suite against the actual live GitHub Pages URL, not just the local file—which is how we confirmed the deployed recon-math.js path and cross-file loading genuinely worked, rather than assuming a local pass would transfer.

How I'd extend this with more time

  • Real fan/cone-beam CT geometry, distinct from PET's parallel-beam model, so the physical difference between modalities shows up in the reconstruction itself, not just the scanner animation.
  • OSEM or a regularized MAP reconstruction alongside MLEM, to show that early stopping isn't the only lever on this tradeoff—algorithmic regularization is another.
  • Upload a real image as a custom phantom and report a quantitative similarity metric (SSIM/PSNR) against it, instead of relying on visual comparison alone.
  • Higher resolution. The in-browser sparse-matrix approach is tuned for 64×64 interactivity; a WASM or server-side path could go to 256×256 without freezing the tab.
  • CI running npm test and the Playwright suite on every push, now that both exist.
